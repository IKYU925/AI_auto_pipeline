# 장애·트러블슈팅 기록

1단계부터 4단계 준비까지(2026-11-13 ~ 2026-11-17) 겪은 문제를 한곳에 모았다. 사례마다 어떤 환경에서 일어났는지, 무엇이 보였고 원인이 무엇이었는지, 어떻게 고쳤는지, 근거가 어디에 있는지를 적는다. 원인을 확인하지 못한 것은 추정이라고 적는다.

자료는 이 저장소의 `docs/worklog`, `docs/retro`, `results/`, 세 저장소(AI_auto_pipeline, infra_local_set, infra_template)의 커밋, 이 맥에 남은 작업 세션 기록이다. 다른 맥북에서 진행한 세션 기록은 이 맥에 없어서, 그 맥에서 일어난 일은 결과 문서에 남은 것만 적었다.

## 1. `git apply`가 패치를 조용히 건너뜀

- **환경.** L1. 1단계 A/B 실험 스크립트가 시나리오마다 shopapi에 버그 패치를 넣는다.
- **증상.** 조건 A 실행이 S02에서 멈췄다. 버그가 들어가지 않아 장애가 재현되지 않았다.
- **원인.** `git apply`를 저장소 하위 폴더에서 실행하면 `diff --git` 형식 패치의 경로를 저장소 루트 기준으로 읽는다. 대상 파일을 찾지 못하면 `Skipped patch`만 출력하고 종료 코드 0을 돌려준다. S01만 일반 diff 형식이라 이전 확인에서 놓쳤다.
- **조치.** 패치 적용 방식을 고치고, 하위 폴더 git 저장소에서 재현하는 회귀 테스트를 넣었다.
- **근거.** 커밋 `cc6bd2f`, `docs/worklog/2026-11-14.tsv`.
- **배운 점.** 종료 코드만 보고 성공을 판정하면 안 된다. 실험 도구는 "주입이 실제로 됐는가"를 따로 확인해야 한다.

## 2. 워커가 큐 대기 중에 죽음

- **환경.** L1. 워커가 Redis Streams(`XREADGROUP`, 5초 대기)로 장애를 받는다.
- **증상.** 할 일이 없을 때 워커가 `TimeoutError`로 죽었다.
- **원인.** redis-py 8의 기본 소켓 시간 제한 5초가 큐 대기 5초와 겹쳤다. 4초 대기는 성공했고, 6초 대기는 5.0초에 `TimeoutError`가 났다(실측).
- **조치.** 소켓 시간 제한을 30초로 늘렸다.
- **근거.** PR #4, 커밋 `b359ba7`, `tests/test_infra.py`.

## 3. LLM API 요청 형식과 모델 확인

- **환경.** EXT(Anthropic API).
- **증상.** Opus 5.5 호출이 400으로 거절됐다. 경량 모델 `claude-haiku-5-5`를 없는 모델로 보고 4.5로 바꾼 적이 있다.
- **원인.** langchain-anthropic이 `temperature=0`을 보냈고 Opus 5.5는 이를 거절한다. Haiku 5.5도 `temperature: Extra inputs are not permitted`로 거절했다(실측). 모델 판단은 당시 참고한 모델표에 의존한 것이 틀렸다.
- **조치.** 모든 모델에서 temperature를 빼고, 모델 목록 API(`GET /v1/models`)로 존재를 확인한 뒤 Haiku 5.5로 되돌렸다.
- **근거.** PR #2, #8, `docs/decisions/0007-light-model-haiku-5-5.md`, worklog 2026-11-13T15:55Z, 20:05Z, 20:25Z 행.

## 4. Slack 연동 세 가지

- **환경.** EXT. Slack Events API, ngrok, n8n, 자동화 API.
- **증상과 원인.**
  - 이벤트가 오지 않았다. Request URL은 Verified인데 사람 메시지 이벤트도 0건이었다. 원인은 Slack 앱의 Socket Mode였다. 켜져 있으면 이벤트가 HTTP가 아니라 소켓으로 간다. 사용자 캡처로 확인하고 끈 뒤 이벤트가 도착했다.
  - 알림이 3,987자와 137자 두 메시지로 쪼개져 스택트레이스 코드 블록이 끊겼다. Slack이 4,000자 근처에서 메시지를 나눈다. shopapi 알림을 3,500자로 제한했다(실측 3,466자 한 메시지).
  - 트레이스백의 `<module>`이 `&lt;module&gt;`로 깨졌다. Slack이 이벤트 본문의 `<`, `>`, `&`를 엔티티로 바꿔 보낸다. n8n 파서에 복원을 넣고, node로 파서를 직접 실행하는 테스트를 만들었다.
- **재발.** 3단계에서 승인 버튼을 받으려고 Socket Mode를 다시 켜자 1단계 n8n 경로가 이벤트를 받지 못했다. 1단계에서 겪은 동작인데 설계 때 바로 떠올리지 못했다(`docs/retro/phase3.md`).
- **근거.** PR #13(커밋 `1b06b0b`, `a8a4947`), `results/phase1_slack.md`.

## 5. 테스트가 실제 Slack으로 회신을 시도

- **환경.** L1.
- **증상.** 테스트 17개가 실패했다. 실험 스크립트와 검증 스택에서는 워커가 `SlackApiError(channel_not_found)`로 멈추고 메시지를 ack하지 않았다.
- **원인.** 테스트와 데모 설정이 개발자의 `.env`를 읽었다. `.env`에 실제 봇 토큰이 들어간 뒤로, 실험용 가짜 채널(`C-EXPERIMENT`)에도 회신을 시도했다. 전송은 SSL 오류로 실제로 나가지 않았다.
- **조치.** 테스트 설정이 `.env`를 읽지 않게 했다. Slack 회신 실패는 처리 결과를 저장한 뒤의 외부 경계 오류이므로 경고로 남기고 워커는 계속 돈다.
- **근거.** 커밋 `d6d048a`, `bc5077e`.

## 6. 측정값이 오염될 뻔한 두 사례

- **환경.** L1.
- **재발 비용 미집계.** 재발 시나리오(S12)는 먼저 base 장애를 처리하고 같은 장애를 다시 넣는다. base 처리 비용(A $0.081, B $0.086)이 총비용과 비용 상한에서 빠져 총비용이 약 $0.17 적게 잡혔다. 다른 모델의 교차 검토로 찾았다. `procedure_usd`로 집계하게 고쳤다(커밋 `97217c9`).
- **회신 수 집계 결함.** 워커 강제 종료 실험의 첫 측정에서 회신 0인 실행이 12건 나왔다. 집계 스크립트가 로그를 stdout에서만 읽고 있었다. 손으로 메우지 않고 두 조건을 처음부터 다시 쟀다. 재측정에서는 모든 실행의 회신이 1이었다(`results/phase2_kill.md`).
- **배운 점.** 숫자를 믿기 전에 그 숫자가 무엇을 쟀는지 확인한다. 1단계 A/B 비용 차이 $0.32도 출처별로 나눠 합이 맞는지 확인한 뒤 보고했다.

## 7. 첫 배포에서 api, 워커가 DB보다 먼저 뜸

- **환경.** L2. 3-2 첫 배포.
- **증상.** api와 워커가 PostgreSQL보다 먼저 떠서 접속에 실패했다. DB가 준비된 뒤에도 커넥션 풀이 30초 `PoolTimeout`을 반복하며 회복하지 못했다.
- **조치.** init container(`python -m app.wait`)가 DB, Redis 준비와 스키마 완료를 기다린 뒤 앱을 시작한다. migrate Job도 api의 init container로 옮겼다. Job은 이미지를 바꿀 수 없어서, 버그 주입 이미지로 재배포할 때 적용에 실패했기 때문이다.
- **근거.** `deploy/k8s/base/aiops.yaml`, `app/wait.py`, worklog 2026-11-14T13:40Z, 20:52Z 행.

## 8. 처리 시간에 모델 다운로드가 섞임, 이미지 크기

- **환경.** L2. 3-3 클러스터에서 S01 첫 측정.
- **증상.** 처리 시간 46.6초 중 약 14초가 워커의 임베딩 모델 첫 다운로드였다.
- **조치.** 모델을 이미지에 넣고 `HF_HUB_OFFLINE=1`로 런타임 다운로드를 막았다. 재측정 26.0초, HuggingFace 요청 0건.
- **곁가지 문제.** 모델 폴더에 `chown -R`을 걸자 모델 253MB가 새 레이어에 한 번 더 담겨 이미지가 1.84GB가 됐다. 같은 `RUN`에서 `chmod a+rX`로 바꿔 1.37GB가 됐다. 런타임에 쓰기 권한이 필요 없다는 것은 `nobody`, `--network none`으로 확인했다.
- **근거.** `results/phase3_s01_cluster.md`, `Dockerfile`, 커밋 `859b7f2`.

## 9. 확인 작업이 api를 OOMKilled로 만듦

## 10. 맥 디스크 상태가 노드 디스크 알림으로 뜸

- **환경.** L2(infra_local_set).
- **증상.** `NodeFilesystemSpaceFillingUp` 알림이 떴는데 노드 디스크 문제가 아니었다.
- **원인.** VM의 `/vagrant`는 맥 폴더를 공유하는 vboxsf다. node-exporter가 이것을 수집해 맥 디스크 상태가 노드 알림으로 올라왔다.
- **조치.** node-exporter의 `fs-types-exclude`에 vboxsf를 더했다. `extraArgs`는 리스트라 차트 기본 인자 두 줄을 옮겨 적었다.
- **근거.** infra_local_set 커밋 `f2edf04`.

## 11. 런북 카테고리 때문에 맞는 런북이 검색되지 않음

- **환경.** L2. 3-5 첫 실제 알림(PodOOMKilled)이 자동화와 Slack 카드까지 이어졌다.
- **증상.** OOM 장애에 기동 실패 런북이 안내됐다.
- **원인.** 분류기가 OOM을 config로 분류했고, OOM 런북은 infra 카테고리에 묶여 검색 후보에서 빠졌다.
- **조치.** Kubernetes 런북의 카테고리를 general로 바꿨다. 클러스터 검색 확인 5/5.
- **근거.** `knowledge/k8s/*.md`, `results/phase3_alert_path.md`.

## 12. 알림 문구만으로는 분류할 수 없었음

## 13. 맥이 잠들면 클러스터 시계가 밀림

- **환경.** L2. VirtualBox VM.
- **증상.** 측정 사이에 맥이 잠들면 VM이 일시 정지되고, 깨어난 뒤 노드 시계가 밀렸다. 한 번은 976초, 다른 한 번은 세 노드 모두 약 2분 늦었다(실측). 감지 시간은 노드 시계로 재므로 측정이 틀어진다.
- **조치.**
  - 실행기가 시작 전에 노드와 Prometheus 시계를 확인하고, 어긋나면 측정을 시작하지 않는다(커밋 `1a4a33d`, `897eee7`).

## 19. 맥 메모리 부족으로 k3s 재시작

- **환경.** L2. 16GB 맥.
- **증상.** 맥에 "메모리 부족" 팝업이 떴다. k3s-cp에서 k3s가 부팅 후 2번 재시작했고(NRestarts=2), 그 여파로 자동화 측정이 두 번 깨졌다. kube-prometheus-stack Helm 릴리스가 `pending-upgrade`로 멈췄다(값이 이전 리비전과 같아 `helm rollback`으로 풀었고, 멈춘 원인은 확인하지 못했다).
- **측정.** 맥 swap 10.2GB/11.3GB 사용. k3s VM 3대 10GB와 Docker Desktop VM 8GB를 합치면 18GB로 맥 RAM을 넘었다. k3s-cp는 2GB 중 available 330MB였다.
- **판단.** 원인은 워크로드 크기가 아니라 VM 배분이다. 클러스터 실제 사용량은 약 5GB였다.
- **조치.** k3s-cp를 3GB로 늘리고 Docker Desktop 메모리를 약 3GB로 낮췄다.
- **결과.** 부팅 직후 cp available 1,562MB, 26분 뒤 1,499MB. 그동안 pgmajfault 5,273에서 5,302, NRestarts 0. 그 사이 S14, S15, S16(노드 정지 3분 포함)이 끝까지 돌았다. 맥 swap 2.5GB/3.1GB.
- **근거.** infra_local_set 커밋 `35e8462`, `docs/mac-memory-2026-11-16.md`, PR #11.

## 20. 장애 하나가 replica 수만큼 따로 접수됨(S15)

- **환경.** L2. S15, 메모리 limit보다 큰 요청으로 shopapi Pod를 OOMKilled.
- **증상.** replica 2개가 모두 OOMKilled되자 장애 1건이 2건으로 접수되고 Slack 카드도 2장 올라갔다.
- **원인 추적.**
  - 처음에는 중복 제거 키가 container, pod 라벨이라고 봤다. 코드를 다시 보니 틀린 판단이었다.

- **조치.**
  - 먼저 같은 Deployment의 Pod 두 개에서 같은 알림이 오는 테스트를 써서 실패로 재현했다.

- **검증.** 클러스터에서 Pod 두 개(`shopapi-587b4c5655-2vvqf`, `-bv5xr`)가 알림을 냈고, 장애 1건과 카드 1장이 됐다. 지문은 분류 캐시 키도 겸하므로 LLM 호출도 한 번으로 줄었을 것이다(추정, 호출 수는 세지 않음).

## 26. EKS 첫 apply가 EBS CSI 애드온에서 멈춤

- **환경.** AWS. infra_template `make eks-up`(envs/aiops-eks/cluster), 2026-11-17 01:06 ~ 01:49 KST.
- **증상.** VPC, EKS 클러스터, 노드 그룹 2개, coredns, kube-proxy까지 만든 뒤 `aws-ebs-csi-driver` 애드온 생성이 400으로 실패했다. ArgoCD와 루트 앱은 그 뒤 단계라 설치되지 않았다.
  ```
  InvalidParameterException: ConfigurationValue provided in request is not supported:
  [$.controller.k8sTagClusterId: is not defined in the schema and the schema does not allow additional properties]
  ```
- **원인.** `cluster/main.tf`가 애드온 설정으로 넘기는 `controller.k8sTagClusterId`를 이 애드온 버전의 설정 스키마가 허용하지 않는다(오류 메시지로 확인). 가짜 AWS(floci)로 검증할 때는 애드온 설정 스키마를 검사하지 않아 드러나지 않은 것으로 본다(추정).
- **같이 본 것.** 노드 그룹 생성이 32분 51초 걸렸다. 실패 직후 노드 2대는 `Ready`였고 나이는 1분 남짓이었다. 지연 원인은 확인하지 않았다.
- **상태.** 클러스터와 노드는 떠 있는 채로 과금 중이었다. 해당 키를 빼고 다시 apply하거나 `make eks-down`으로 지우는 것이 다음 일이다.
- **근거.** 이 세션에서 읽은 `make eks-up` 로그, `kubectl get nodes`, `kubectl get ns`(argocd 없음).
