# 1단계 회고 자료

velog 1편 초안의 재료다. 수치와 근거는 results/와 docs/decisions/에 있다.

## 만든 것

- 대상 서비스 shopapi(주문, 쿠폰, 재고, 결제, 목록)와 장애 시나리오 13종. 버그는 패치로 주입하고, 수정이 맞았는지는 LLM이 볼 수 없는 숨은 테스트로 판정한다.
- 시나리오가 제대로 만들어졌는지 검사하는 스크립트(버그가 공개 테스트를 통과하는지, 숨은 테스트만 잡는지). 이것 자체를 테스트에 넣었다.
- 최적화 다섯 가지를 끌 수 있는 서버 설정과, 서버 설정이 기록하려는 조건과 같은지 확인하고 반복 실행해 CSV를 남기는 실험 스크립트.
- Slack 알림, n8n, 자동화, 스레드 회신까지 이어지는 실연동.

## 숫자

- 최적화를 켜면 장애당 LLM 비용이 $0.088에서 $0.063으로 28% 낮다. 비코드 장애는 건당 $0.044에서 $0.0003, 재발은 LLM 0회.
- 코드 버그 9종 모두 첫 시도에 수정(A). 알림부터 Slack 회신까지 25~31초.
- 실험 전체 실제 API 비용 약 $2.8.

## 실패와 배운 것

- 시그니처가 어긋난 버그에서 LLM은 6회 중 5회 "통과하지만 틀린" 수정을 냈다. 인자를 받아서 버리거나, 호출하는 쪽에서 인자를 지웠다. 숨은 테스트가 없었다면 성공으로 집계됐다. 자동 수정을 사람이 승인할 때 무엇을 봐야 하는지가 다음 과제다.
- 실험 도구의 버그가 결과를 오염시킬 뻔했다. 저장소 하위 폴더에서 `git apply`가 diff --git 형식 패치를 조용히 건너뛰어(종료 코드 0) S02~S09에 버그가 주입되지 않았다. 재현 단계에서 멈춰 잡았다.
- 재발 시나리오가 base 처리 비용을 집계하지 않아 총비용이 약 $0.17 적게 잡혔다. 다른 모델의 교차 검토로 찾았다.
- 실제 운영 환경에서만 드러난 문제: redis-py 8의 기본 소켓 제한(5초)과 큐 대기 5초가 겹쳐 워커가 죽음, Slack이 4,000자 넘는 알림을 나눠 올려 스택트레이스가 끊김, Slack 앱의 Socket Mode가 켜져 있으면 이벤트가 오지 않음, 테스트가 개발자 .env의 실제 Slack 토큰을 읽음.
- 모델 이름을 기억에 의존했다가 틀렸다(Haiku 5.5를 없는 모델로 판단). 모델 목록 API와 요금 페이지로 확인하는 것으로 바꿨다.

## 결정

- 실제 API 비용 때문에 A/B를 조건마다 1회로 줄였다(decisions/0010). 결과가 갈린 S08만 3회로 늘렸다.
- 결과를 본 뒤 시나리오 기대값을 고치지 않았다(decisions/0011). S10을 dependency로 분류한 것은 그대로 오답으로 셌다.
