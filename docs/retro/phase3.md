# 3단계 회고 자료

velog 3편 초안의 재료다. 수치와 근거는 results/phase3_summary.md, docs/features/F11~F14, F06, docs/decisions/에 있다.

## 만든 것

- 로컬 K3s(Vagrant 3노드)에 자동화(api, worker 2개, approvals, PostgreSQL, Redis)와 shopapi 세 벌(shop, tenant-a, tenant-b), 관측 도구(kube-prometheus-stack, Loki, Alloy)를 올렸다. 클러스터는 형제 저장소 infra_local_set이 Ansible로 만든다.
- 감지 경로: PrometheusRule과 Loki ruler가 Alertmanager로, Alertmanager가 자동화 웹훅으로 알림을 보낸다. 알림 종류 표(`app/alerts.py`) 하나가 알림마다 대상, 스택트레이스 조회, Pod 마지막 로그, 조치를 정한다.
- 장애를 실제로 넣고 구간별 시간을 재는 실행기(`scripts/run_cluster.py`): 버그 이미지 배포, 설정 변경, 메모리 제한, 노드 전원 차단, 워커 Pod 강제 삭제, 디스크 채우기, 사람 승인 대기.
- Grafana 대시보드 2개(자동화 현황과 SLI, shopapi)와 SLI 정의(`docs/sli.md`), SLI 계산 스크립트.
- 고객사 분리: namespace로 고객사를 정하고, 지문, 회신 채널, 런북 검색 범위가 고객사를 넘지 않게 했다.
- 승인 후 조치: 허용 목록 조치만 카드에 버튼으로 붙이고, Slack Socket Mode로 클릭을 받아 노드 플레이북 Job이나 Deployment 롤백을 실행한다. 승인자와 결과를 `actions`에 남긴다.

## 숫자

- 장애 발생부터 Slack 회신까지 중앙값: 코드 버그 120초, 설정·인프라 장애 264초. 처리 자체는 27초, 2.2초이고 나머지는 감지와 전달이다.
- 설정·인프라 알림 런북 안내 5/5. 분류는 처음 0/4였다가 Pod 마지막 로그를 붙인 뒤 4/4.
- 실패 요청 50회가 알림 1개, 장애 1건으로 합쳐졌다.
- 워커 Pod를 강제 삭제하면 43초 뒤 다른 워커가 이어 처리했다. 추가 LLM 호출 0, 중복 회신 0.
- 같은 버그를 두 고객사에 넣으면 각 고객사 채널로 1건씩, 다른 고객사 문서 0.
- 승인 후 조치: 노드 디스크 정리는 승인부터 해소까지 29초, 배포 직후 장애 롤백은 승인부터 롤백 끝까지 6초(알림 해소까지 119초).
- 3단계 실험 전체 실제 API 비용 약 $1.2.

## 실패와 배운 것

- **회신이 두 번 갔다.** 노드 장애 재개 실험(S16)에서 한 워커가 회수 기준(30초)보다 오래 처리하자 다른 워커가 같은 메시지를 회수해 둘 다 회신했다. 3-7에서는 회신 수를 세지 않아 놓쳤고, 3-8에서 처리 중 메시지를 붙잡는 heartbeat를 넣어 고쳤다. 재개 실험은 "이어서 처리했나"뿐 아니라 "한 번만 회신했나"를 세야 한다.
- **알림 문구만으로는 분류할 수 없었다.** CrashLoop 알림은 "Pod is crash looping." 한 줄이다. 결과(런북 안내)는 맞았지만 분류는 근거 없이 찍은 것이었다. Pod 마지막 로그를 붙이자 4/4가 됐다.
- **맥이 잠들면 클러스터가 멈춘다.** VirtualBox VM이 일시 정지되고 노드 시계가 밀렸다(한 번은 976초). 감지 시간이 시계에 의존하므로 실행기가 시작 전에 시계를 확인하고, 실행은 `caffeinate`로 감쌌다.
- **측정이 측정하려던 것을 재지 않았다.** 배포 직후 롤백(S20) 첫 실행에서 버그 요청을 한 번만 보내, 오류 로그 알림이 승인보다 143초 먼저 저절로 해소됐다. 롤백 효과가 아니었다. 롤백 전까지 버그 요청을 이어 보내도록 바꾸고 다시 쟀다. 실행기는 이제 승인 전 해소를 음수 대신 그대로 적는다.
- **전달 시간의 30초를 끝까지 설명하지 못했다.** group_wait 30초 외에 규칙 평가기에서 Alertmanager로 보내기 전 30초가 더 있었다(3-8). 3-9에서는 사라졌고 3-10에서는 다시 있었다. 원인은 남았다.
- **Socket Mode와 n8n 경로가 충돌한다.** 승인 버튼을 받으려고 Socket Mode를 켜면 Slack 이벤트가 소켓으로 와서 1단계의 n8n 경로가 이벤트를 받지 못한다. 1단계에서 한 번 겪은 동작인데, 3-10 설계 때 바로 떠올리지 못했다.
- **git add가 조용히 실패했다.** 이미 옮긴 경로를 `git add`에 넣어 첫 커밋에서 매니페스트가 빠졌다. 커밋 뒤 `git status`로 남은 파일이 없는지 확인하는 습관이 필요하다.

## 결정

- 4단계를 EC2와 CloudWatch에서 EKS로 바꿨다(decisions/0014). EC2 경로로는 Pod 장애, 배포 이력, 롤백을 다룰 수 없었다. SQS 입구는 floci로 동작을 확인했지만 PR을 닫았다.
- AWS 리소스는 이 저장소에 두지 않고 infra_template이 맡는다. 클러스터 수명(만들고 지우기, TTL 삭제)도 그쪽 몫이다.
- 조치는 런북이 아니라 알림 종류 표에서 정한다. 런북은 검색 결과라 질의에 따라 뽑히는 문서가 달라진다.
- 노드 주소는 알림 라벨이 아니라 허용 목록에서 가져온다. 롤백 대상 리비전은 제안할 때 고정하고, 승인 때 리비전이 다르면 실행하지 않는다.
- rollout restart는 넣지 않았다. 지금 시나리오 중 restart로 풀리는 장애가 없다.
- SLI는 지금 정의하고 SLO 목표는 4단계에서 정한다. 로컬 실험 값으로 목표를 정하면 의미가 없다.
- shop(공통 환경)을 고객사로 대체하지 않고 남겼다. 3-7, 3-8 실행기와 대시보드를 그대로 재현할 수 있다.
