# F01. 장애 시나리오와 판정

상태: 완료(S12, S13 실행 절차는 F02)
관련: plan.md 3장, 4장, Day 1~2

## 문제

자동화가 장애를 제대로 처리했는지 숫자로 말하려면, 정답이 정해진 장애를 같은 조건으로 반복해서 일으키고 결과를 판정할 수 있어야 한다. 정답을 아는 사람이 직접 고르면 쉬운 장애만 남고, 자동화가 고른 테스트만으로 판정하면 엉뚱한 수정도 통과한다.

## 목표와 비목표

- 목표: 시나리오마다 버그 주입, 장애 재현, 정답 판정을 스크립트로 반복할 수 있게 한다.
- 목표: 시나리오가 올바르게 만들어졌는지(버그가 공개 테스트에 걸리지 않고 숨은 테스트에만 걸리는지)를 자동으로 검사한다.
- 비목표: 지표 수집과 A/B 실행(F02), 실제 알림 경로(F04, F07).

## 운영자 시나리오

1. `scripts/inject.sh S02`로 버그를 넣는다.
2. 시나리오의 요청을 shopapi에 보내면 500과 스택트레이스가 나온다.
3. 자동화가 분석, 수정, 검증을 마친다.
4. AI 패치를 숨은 테스트와 전체 테스트로 판정하고 버그를 원복한다.

## 요구사항

- 시나리오 정의(`scenarios/<ID>.yaml`): `id`, `title`, `type`(code_bug, infra, config, recurrence, duplicate), `difficulty`, `expected`, 재현 방식 하나, 코드 버그면 `hidden_test`.
- `expected`: `outcome`은 필수. `category`, `needs_code_fix`, `root_cause_file`, 재발의 `llm_calls`, 중복의 `incidents_created`는 해당 시나리오만 쓴다.
- 재현 방식은 아래 다섯 가지 중 정확히 하나만 둔다. 둘 이상이거나 없으면 읽을 때 오류다.

| 키 | 장애 정보를 만드는 방법 | 시나리오 |
| --- | --- | --- |
| `requests` | 버그가 든 shopapi에 요청을 순서대로 보내 처음 난 예외와 스택트레이스 | S01~S09 |
| `startup` | 지정한 환경변수를 지우고 shopapi를 기동해 난 예외와 스택트레이스 | S11 |
| `alert` | 모니터링 알림 문구만(스택트레이스 없음) | S10 |
| `recurrence` | base 시나리오를 처리한 뒤 같은 장애가 다시 들어옴 | S12 |
| `duplicate` | base 시나리오의 알림이 짧은 시간에 여러 번 들어옴 | S13 |
- 버그 패치(`scenarios/<ID>.patch`): `targets/shopapi` 기준 상대 경로의 unified diff.
- 숨은 테스트(`scenarios/hidden_tests/test_<id>.py`): 버그가 깨뜨리는 스펙을 검증한다. 공개 테스트에는 같은 스펙을 두지 않는다.
- 코드 버그 시나리오는 버그가 공개 테스트를 깨지 않아야 한다. 실제로 배포된 버그는 기존 테스트를 통과한 버그이기 때문이다.

## 설계 메모

- 시나리오마다 버그를 깨는 공개 테스트가 있으면 그 테스트를 숨은 테스트로 옮긴다. 공개 테스트 수는 줄지만 "배포된 버그"라는 전제를 지킨다.
- 버그 패치는 shopapi를 직접 고친 뒤 `scripts/capture_patch.sh <ID>`로 diff를 저장하고 원복한다. diff를 손으로 쓰지 않는다.
- `reproduce`는 시나리오마다 shopapi를 새로 import한다. 한 프로세스에서 여러 시나리오를 검사하기 위해서다.
