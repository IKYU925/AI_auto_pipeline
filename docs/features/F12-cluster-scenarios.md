# F12. 클러스터 감지 경로 시나리오 실행과 시간 측정

상태: 완료
관련: plan.md 9-6, 3-7

## 문제

1, 2단계 측정은 실험 스크립트가 장애를 API로 바로 접수했다. 3단계에서는 장애가 클러스터에서 실제로 나고, 모니터링이 감지해 알림을 보내고, 자동화가 받아 처리한 뒤 Slack에 회신해야 한다. 이 경로의 시간(감지, 전달, 처리, 회신)을 잴 도구가 없고, Kubernetes 장애 시나리오(S14~S16)도 없다.

## 목표와 비목표

- 목표: 시나리오마다 클러스터에 장애를 넣고, 알림 시작, 자동화 수신, 처리 완료, Slack 회신 시각을 한 줄로 남긴다.
- 목표: S14(잘못된 설정값으로 기동 실패 반복), S15(메모리 초과), S16(워커 노드 장애) 시나리오 파일.
- 목표: 끝나면 클러스터를 매니페스트 상태로 되돌린다.
- 비목표: S17 노드 디스크(3-10에서 승인 조치와 함께).

## 운영자 시나리오

1. `scripts/run_cluster.py S01 S14 --max-usd 1 --out results/phase3.csv`를 실행한다.
2. 스크립트가 시나리오마다 장애를 넣고, 알림이 자동화로 넘어가 처리되고 회신될 때까지 기다린 뒤, 클러스터를 되돌리고 다음 시나리오로 간다.
3. 결과 CSV에서 감지 시간과 전체 처리 시간을 본다. 코드 버그는 숨은 테스트 채점(`hidden_passed`, `full_passed`, `false_pass`)도 본다. 채점은 클러스터가 아니라 로컬 shopapi 복사본에서 한다.

## 요구사항

- 시나리오 YAML의 `cluster` 블록이 클러스터에서 장애를 만드는 방법이다. 없으면 코드 버그 기본값(버그 이미지 배포 후 `requests` 전송, `ShopapiException`)을 쓴다.
  - `alert`: 기다릴 알림 이름
  - `env`: shopapi 환경변수 변경. 값이 null이면 지운다
  - `memory_limit`: shopapi 메모리 limit
  - `traffic`: 반복해서 보낼 요청과 시간(`every_sec`, `for_sec`)
  - `node_halt`: 멈출 VM과 멈춰 둘 시간(S16)
- 장애 정보에 알림 시작 시각을 남긴다(`incidents.occurred_at`). 지금은 접수 때 버려진다.
- 측정값
  - 감지 시간: 장애 주입부터 알림 시작(`occurred_at`)까지
  - 전달 시간: 알림 시작부터 자동화 수신(`created_at`)까지
  - 처리 시간: 수신부터 완료(`finished_at`)까지
  - 전체 시간: 장애 주입부터 Slack 회신(`report_ts`)까지
- 시작 전에 클러스터에 자동화로 가는 firing 알림이 없을 때까지 기다린다. 같은 알림이 열려 있으면 새 장애가 접수되지 않는다.
- 누적 LLM 비용이 `--max-usd`에 닿으면 남은 시나리오를 멈춘다.

## 설계 메모

- 되돌리기는 `kubectl apply -k`로 매니페스트 상태를 다시 적용한다. 바꾼 값을 하나씩 원복하는 것보다 실패해도 같은 상태로 수렴한다.
- S14는 "잘못된 Secret"을 shopapi가 기동 때 읽는 설정값의 형식 오류(`PG_TIMEOUT_SEC=3s`)로 만든다. shopapi는 `PG_API_KEY`의 값 자체는 검사하지 않아서, 키 값을 바꿔서는 기동 실패가 나지 않는다.
- S10은 결제 대행사 주소를 응답 없는 주소로 바꾸고 제한 시간을 8초로 늘려 실제로 결제를 느리게 만든다. 이때 타임아웃 예외도 나므로 `ShopapiException`이 함께 뜰 수 있다. 그대로 기록한다.
