# F13. 반복 알림 합치기, 설정·인프라 알림 분류, 워커 종료 중 재개, 3단계 결과 분석

상태: 완료
관련: plan.md 9-4, 9-6, 9-9, 3-8, [SLI 정의](../sli.md)

## 문제

3-7 측정에서 다음이 남았다.

- 설정·인프라 장애(코드를 고쳐서는 풀리지 않는 장애) 알림 4건의 분류가 모두 틀렸다. CrashLoop 알림은 "Pod is crash looping." 한 줄이라 판단 근거가 없다.
- S16에서 노드 장애 전에 걸어 둔 장애가 분석 시작 전이라, 분석 도중 체크포인트에서 이어 가는지 확인하지 못했다.
- 같은 S16에서 그 장애가 Slack에 두 번 회신됐다. 3-7 요약은 이를 놓쳤다.
- plan.md 9-9의 반복 알림 합치기(같은 원인의 실패 요청 50회가 장애 1건이 되는지), 워커 Pod 강제 삭제 재개 실험을 하지 않았다.
- 자동화가 잘 돌고 있는지 한눈에 볼 기준(SLI)이 없다.

## 목표와 비목표

- 목표: CrashLoop, OOMKilled 알림에 대상 Pod의 마지막 로그를 붙여 분류 근거로 쓴다.
- 목표: 한 장애가 두 번 회신되지 않는다.
- 목표: 반복 알림 합치기, 워커 Pod 강제 삭제, S16 분석 도중 노드 정지 실험을 실행하고 기록한다.
- 목표: 자동화 SLI를 정의하고 지금 데이터로 계산한다. 대시보드 첫 줄을 SLI로 바꾼다.
- 목표: 3단계 결과 표(plan.md 11장 양식)를 채운다.
- 비목표: SLO 목표치, burn rate 알림(4단계). 고객사 분리(3-9), 승인 조치(3-10).

## 사용 시나리오

1. 설정·인프라 장애가 나면 회신 카드의 분류가 원인(설정, 인프라)과 맞고, 맞는 런북이 붙는다.
2. 워커 Pod가 분석 도중 죽어도 다른 워커가 이어 받아 회신은 한 번만 간다.
3. Grafana 자동화 대시보드 첫 줄에서 회신이 제때 가고 있는지, 처리가 멈춘 장애가 있는지 본다.

## 요구사항

- Alertmanager 어댑터는 `KubePodCrashLooping`, `PodOOMKilled` 알림이면 Loki에서 그 Pod의 마지막 로그 40줄을 꺼내 장애 정보(`logs`)에 붙인다. 조회에 실패해도 접수는 한다.
- 장애 지문에 마지막 로그 줄을 넣는다. 알림 문구가 같아도 원인이 다른 CrashLoop은 다른 장애다.
- 분류 프롬프트의 유형 정의를 시나리오와 런북의 분류 기준에 맞춘다(외부 연동 지연은 infra, 기동 중 설정 오류는 config).
- 워커는 처리하는 동안 메시지의 유휴 시간을 회수 기준의 1/3마다 0으로 되돌린다. 회수는 한 번에 하나씩 한다.
- 실행기 옵션
  - `--burst N`: S13의 실패 요청 수. 자동화로 간 알림 수, 웹훅 전송 수, 생성된 장애 수를 남긴다.
  - `--kill-worker-after TASK`: 그 단계 LLM 호출이 끝나면 처리 중인 워커 Pod를 강제 삭제한다.
  - `--halt-after TASK`: S16에서 걸어 둔 장애의 그 단계가 끝나면 노드 전원을 끈다.
  - 재개 기록: 재개한 단계, 단계별 호출 수, 중단 뒤 첫 호출과 완료까지 시간, 회신 채널의 Slack 메시지 수

## 설계 메모

- 근거 로그는 스택트레이스 칸이 아니라 따로 둔다. 스택트레이스는 근본 원인 분석의 코드 위치 추출에 쓰여서, 기동 실패 로그를 넣으면 설정 문제를 코드 문제로 읽을 수 있다.
- 지문에는 로그 전체가 아니라 마지막 줄만 넣는다. 로그에는 요청마다 바뀌는 값이 많아 전체를 넣으면 같은 장애가 반복될 때 묶이지 않는다.
- 중복 회신은 회신 직전에 `report_ts`를 원자적으로 선점해서도 막을 수 있다. 그러나 원인은 살아 있는 워커의 메시지를 다른 워커가 가져간 것이라, 메시지를 붙잡아 두는 쪽을 고쳤다. 회신과 `report_ts` 저장 사이에 워커가 죽는 좁은 틈은 plan.md 8장대로 남긴다.
