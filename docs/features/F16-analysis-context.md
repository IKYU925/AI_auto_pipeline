# F16. 분석 컨텍스트(배포 이력, Pod 상태와 K8s 이벤트)

상태: 완료
관련: plan.md 10장(P4), 4-3

## 문제

분석 입력은 알림 문구, 스택트레이스, (CrashLoop, OOM이면) Pod 마지막 로그뿐이었다. 그래서 두 가지를 못 한다.

- 배포 직후에 난 장애에서 "방금 배포가 원인일 수 있다"를 모른다. 롤백이 가장 빠른 완화인데 근거가 없다.
- 이미지 받기 실패처럼 컨테이너가 뜨지 않는 장애는 로그도 스택트레이스도 없다. S21 분류 신뢰도가 0.50(코드 수정 경로로 넘어가는 기준과 같은 값)이었다.

## 목표와 비목표

- 목표: 알림 시점의 배포 이력(현재와 직전 리비전, 이미지, 장애 몇 분 전)을 원인 분석에 넣는다.
- 목표: Pod 알림이면 컨테이너 상태(대기 사유, 재시작, 직전 종료 사유)와 그 Pod의 K8s 이벤트를 분류와 원인 분석에 넣는다.
- 목표: 조회가 실패해도 접수는 한다. 근거만 빠진다.
- 비목표: 노드나 클러스터 전체 이벤트. 이번에는 알림 대상 Pod만 본다.

## 요구사항

- 배포 이력(`app/deploys.py`): Deployment에 ArgoCD 추적 표시(`argocd.argoproj.io/tracking-id`)가 있으면 그 Application의 배포 이력에서, 없으면 ReplicaSet에서 읽는다. 로컬과 EKS가 같은 코드로 돈다.
- Pod 컨텍스트(`app/pod_events.py`): `pod` 라벨이 있는 알림이면 Pod 상태와 이벤트(최근 순, 최대 10개, 메시지 300자)를 텍스트로 만든다. Pod가 이미 지워졌으면 이벤트만 읽는다.
- 둘 다 접수 때 읽어 `IncidentIn.deploy`, `IncidentIn.events`로 큐 메시지에 싣는다. DB 스키마는 바뀌지 않는다.
- 권한: `aiops-deploy-read` ClusterRole(deployments, replicasets, pods, events 읽기)을 shopapi namespace의 RoleBinding으로만 준다. ArgoCD Application 읽기는 고객사 shopapi 앱 이름으로만 준다.

## 설계 메모

- **텍스트로 만들어 싣는다.** 프롬프트에 넣을 형태로 접수 때 만들면 워커는 칸 하나만 더하면 된다. 구조화된 이벤트를 워커까지 넘길 이유가 아직 없다.
- **알림 종류 표에 플래그를 더하지 않았다.** `pod` 라벨이 있으면 읽는다. Pod 알림은 모두 이 근거가 쓸모 있다.
- **런북 안내 경로에서는 원인 분석이 돌지 않는다.** S21은 분류 단계에서 끝나 이벤트가 분류에만 쓰였다. 원인 분석에도 칸을 넣어 두었지만 EKS에서 그 경로는 확인하지 않았다.
