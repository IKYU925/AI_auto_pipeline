# F14. 고객사 분리(tenant-a, tenant-b)

상태: 완료
관련: plan.md 9-7, 3-9

## 문제

MSP는 한 운영 조직이 여러 고객사 환경을 맡는다. 지금 자동화는 고객사를 모른다. 같은 버그가 두 고객사에서 나면 두 번째 장애는 지문이 같아서 첫 장애에 묶이고(중복 제거 10분), 분류 캐시와 수정안 재사용도 고객사를 넘는다. 회신은 모두 한 채널로 가고, 런북 검색은 모든 고객사 문서를 본다.

## 목표와 비목표

- 목표: 고객사 namespace 두 개(tenant-a, tenant-b)에 shopapi를 1개씩 올린다.
- 목표: 장애에 고객사를 붙이고, 회신은 고객사 채널로, 런북 검색은 자기 고객사와 공통 문서로 좁힌다.
- 목표: 중복 제거, 분류 캐시, 수정안 재사용이 고객사를 넘지 않는다.
- 목표: 대시보드를 고객사별로 나눠 본다.
- 비목표: 고객사별 클러스터나 계정 분리. 실제 MSP는 고객사마다 클러스터나 클라우드 계정이 다른 경우가 많다. 여기서는 namespace 분리로 자동화의 라우팅과 검색 범위만 검증한다.
- 비목표: 고객사별 접근 권한(RBAC), 고객사별 비용 청구.

## 사용 시나리오

1. tenant-a의 shopapi에서 장애가 나면 회신이 `#tenant-a-ops`에만 온다. 회신의 근거 문서에 tenant-b 문서가 없다.
2. 몇 분 뒤 tenant-b에서 같은 버그가 나도 새 장애로 접수되어 `#tenant-b-ops`에 따로 회신된다.
3. shop(운영 조직 공통 환경)과 노드 장애는 지금처럼 `#aiops-report`로 간다.

## 요구사항

- 고객사는 알림의 namespace가 `tenant-`로 시작하면 그 이름, 아니면 `common`이다(`app/tenants.py`).
- 회신 채널은 `TENANT_SLACK_CHANNELS`(JSON)에서 고객사로 찾고, 없으면 `ALERT_SLACK_CHANNEL`이다.
- 장애 지문에 고객사를 넣는다.
- 지식 문서 front matter의 `tenant`를 `documents.tenant`(마이그레이션 0004)에 저장한다. 없으면 `common`이다. 검색은 `tenant IN (자기 고객사, common)`만 본다.
- 장애 기록에 근거로 쓴 문서 ID(`result.context_doc_ids`)를 남긴다.
- Alertmanager 라우팅은 infra_local_set에서 두 namespace를 더한다(infra PR #6).

## 설계 메모

- **shop을 남겼다.** plan.md 9-7은 shop을 고객사로 대체한다고 적었다. 메모리를 아끼려는 것이었는데, k3s-w1의 메모리 요청은 31%(1200Mi/3.8Gi)라 shopapi 2개(요청 192Mi)를 더해도 여유가 있다. shop을 남기면 3-7, 3-8 실행기와 대시보드를 그대로 재현할 수 있다. shop은 운영 조직 공통 환경(`common`)으로 본다.
- **shopapi 한 벌을 namespace만 바꿔 쓴다.** `deploy/k8s/shopapi`를 shop과 `deploy/k8s/tenants/*`가 함께 쓴다. 고객사는 replica 1개와 Ingress 호스트만 다르다. 매니페스트를 고객사마다 복사하면 금방 어긋난다.
- **지문에 고객사를 넣는 것 하나로 세 곳을 막는다.** 중복 제거 키, 분류 캐시 키, 수정안 재사용 키가 모두 지문이다. 같은 코드라도 고객사마다 배포 시점이 다를 수 있어서, 다른 고객사의 검증된 수정안을 그대로 재사용하지 않는다.
- **노드 장애는 공통이다.** 노드는 고객사가 함께 쓰는 자원이라 운영 조직 채널로 보낸다.

## 열린 질문

- Alertmanager 라우팅에 앱의 알림 이름과 namespace 목록이 들어 있어서, 고객사나 알림을 더할 때마다 infra 저장소 PR이 필요하다. prometheus-operator의 `AlertmanagerConfig`로 라우팅을 이 저장소로 옮길지 3-10에서 정한다.
