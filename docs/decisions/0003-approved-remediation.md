# 0003. 승인 후 허용 목록 Ansible 플레이북으로 조치한다

상태: 채택
날짜: 2026-11-14

## 맥락

처음 계획은 자동화가 런북 안내까지만 하고 조치는 사람이 직접 하는 것이었다. 운영 자동화에서는 안내 다음 단계인 조치 실행까지 이어지는 흐름이 중요하다.

## 결정

비코드 장애에서 런북에 조치 이름이 있으면 Slack 회신에 승인 버튼을 붙인다. 승인되면 aiops namespace의 Kubernetes Job이 허용 목록에 있는 Ansible 플레이북 하나를 노드 하나에만 실행한다. 범위는 3단계 로컬 노드의 OS 수준 정리 작업(로그와 임시 파일 정리, 서비스 재시작)이다.

## 근거

- 승인 없이 실행하지 않으므로 잘못된 분류가 바로 조치로 이어지지 않는다.
- 플레이북 이름과 대상은 장애 기록에서만 가져오고 LLM 출력은 쓰지 않는다. LLM이 실행할 명령을 정하지 못한다.
- 클러스터 구성에 이미 Ansible을 쓰고 있어 같은 도구로 조치까지 이어진다.
- Job으로 실행하면 실행 기록과 로그가 남고, 자동화 서비스 계정은 Job 생성 권한만 가진다.

## 영향

- `actions` 테이블(승인자, 시각, 결과, 로그)과 S17 노드 디스크 부족 시나리오가 생겼다.
- infra_local_set에 실험용 1GB 볼륨을 만드는 Ansible 작업이 필요하다.
- 쿠버네티스 객체 변경과 AWS 리소스 조치는 계속 하지 않는다.

## 검토한 대안

- 안내만 하기: 조치 흐름을 보여 주지 못한다.
- 승인 없는 자동 조치: 분류 오류가 바로 장애로 이어질 수 있다.
- 자동화 Pod에서 직접 SSH 실행: 권한과 실행 기록을 분리하기 어렵다.
