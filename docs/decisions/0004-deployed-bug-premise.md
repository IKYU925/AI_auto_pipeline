# 0004. 코드 버그 시나리오는 "배포된 버그"를 전제로 만든다

상태: 채택
날짜: 2026-11-14

## 맥락

코드 버그 시나리오는 정상 shopapi에 버그 패치를 넣어 만든다. 처음 만든 S02~S06은 기존 공개 테스트가 버그를 바로 잡았다. 그러면 자동화가 고른 테스트만 돌려도 버그가 드러나서, "선별 테스트는 통과했지만 실제로는 틀린 수정(거짓 통과)"을 측정할 수 없다.

## 결정

실제로 배포된 버그는 기존 테스트를 통과한 버그라는 전제를 지킨다. 버그를 잡는 공개 테스트가 있으면 그 테스트를 시나리오의 숨은 테스트로 옮긴다. 이 조건은 `scripts/check_scenarios.py`가 시나리오마다 확인하고, 파이프라인 테스트(`tests/test_scenarios_valid.py`)에 들어 있어 shopapi나 공개 테스트를 고칠 때 깨지면 바로 실패한다.

## 근거

- 공개 테스트가 버그를 잡으면 자동 수정 성공률이 실제보다 높게 나오고 거짓 통과가 0으로 나온다.
- 손으로 지키는 규칙은 시나리오가 늘면 깨진다. 검사 스크립트가 S02~S06 다섯 개를 모두 "공개 테스트가 버그를 잡는다"로 잡아낸 것이 실제 사례다.

## 영향

- shopapi 공개 테스트 수는 41개(Day 1)에서 34개(S02~S06, PR #3), 40개(S07, S09용 기능 추가, PR #5), 39개(S08, PR #6)로 바뀌었다.
- 공개 테스트 수만 보면 커버리지가 낮아 보인다. 공개와 숨은 테스트를 합친 것이 shopapi의 전체 스펙이다.
- 버그와 숨은 테스트를 같은 사람이 만들므로 판정은 출제자 기준이다. 결과를 보고할 때 이 한계를 함께 적는다(plan.md 10장의 "직접 출제한 시나리오" 리스크와 같은 문제).

## 검토한 대안

- 공개 테스트를 그대로 두고 버그를 다른 경로에 넣기: 시나리오마다 억지스러운 버그가 되고, 일부 스펙은 피할 수 없다.
- 숨은 테스트 없이 전체 테스트로만 판정: 공개 테스트가 스펙을 덜 담고 있으면 틀린 수정도 통과한다.
