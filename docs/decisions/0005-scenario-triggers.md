# 0005. 시나리오 재현 방식을 다섯 가지로 나눈다

상태: 채택
날짜: 2026-11-14

## 맥락

S01~S09는 버그가 든 shopapi에 요청을 보내 난 예외로 장애를 만든다. S10(외부 PG 지연), S11(환경변수 누락), S12(재발), S13(중복)은 예외 요청으로 재현되지 않는다.

## 결정

시나리오 정의에 재현 방식을 정확히 하나 둔다. `requests`(요청 예외), `startup`(기동 예외), `alert`(알림 문구), `recurrence`(base 처리 후 같은 장애 재접수), `duplicate`(같은 알림 N회 접수). 둘 이상이거나 없으면 정의를 읽을 때 오류다.

## 근거

- 재현 방식마다 필요한 값이 달라서(요청 목록, 지울 환경변수, 알림 문구, base와 횟수) 한 형식에 선택 필드를 늘리면 잘못된 조합이 생긴다.
- S10은 실제 지연을 만들지 않고 알림 문구로 들어온다. 1, 2단계 측정은 장애를 API로 접수하므로 같은 문구를 반복하는 편이 측정이 정확하다. 실제 지연을 감지하는 경로는 3단계 Prometheus 규칙에서 다룬다.
- S11은 실제 기동 예외와 스택트레이스를 쓴다. 꾸며낸 스택트레이스로 분류를 측정하지 않기 위해서다.

## 영향

- 실행 스크립트와 검사 스크립트가 재현 방식별로 분기한다(F01, F02).
- 재발과 중복은 절차가 다른 시나리오에 의존한다. base가 코드 버그 시나리오인지는 검사 스크립트가 확인한다.

## 검토한 대안

- S10을 느린 가짜 PG로 실제 지연 재현: shopapi는 지연을 504로 정상 처리해 예외가 없고, 알림은 모니터링이 만드는 것이라 1, 2단계 범위가 아니다.
