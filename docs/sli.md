# 자동화 파이프라인 SLI

이 문서는 장애 자동화 파이프라인이 "잘 돌고 있는지"를 재는 지표(SLI)를 정의한다. SLO는 일정 기간의 실제 트래픽이 있어야 의미가 있다. 운영 트래픽이 없어서 실측에서 출발한 초기 목표(가설)만 아래 "초기 목표" 절에 둔다. 지금 정의해 두는 이유는 4단계에서 계산할 데이터가 실제로 쌓이는지 로컬에서 미리 확인하기 위해서다.

## 누구의 관점인가

파이프라인의 사용자는 Slack으로 장애 회신을 받는 담당 개발자다. 그 사람이 묻는 질문은 네 가지다.

1. 장애를 놓치지 않았나
2. 빨리 알려 줬나
3. 판단이 맞았나
4. 처리하다 멈추지 않았나

SLI는 이 질문마다 "좋은 이벤트 수 / 전체 이벤트 수"로 정의한다. 평균 대신 비율을 쓰는 이유는 평균이 느리거나 틀린 소수를 가려서다.

## SLI

| SLI | 질문 | 좋은 이벤트 / 전체 이벤트 | 데이터 | 지금 측정 |
| --- | --- | --- | --- | --- |
| 커버리지 | 놓치지 않았나 | 장애로 접수된 알림 / 자동화로 라우팅된 알림 | Alertmanager 알림 기록, `incidents.alert_fingerprint` | 불가. 웹훅 전달로 근사 |
| 웹훅 전달 | 놓치지 않았나 | 성공한 웹훅 전송 / 전체 웹훅 전송 | Prometheus `alertmanager_notifications_total`, `alertmanager_notifications_failed_total` | 가능 |
| 회신 시간(코드 버그) | 빨리 알려 줬나 | 알림 시작부터 3분 안에 회신한 장애 / 회신한 장애 | `incidents.occurred_at`, `report_ts`, `needs_code_fix` | 가능 |
| 회신 시간(설정·인프라 장애) | 빨리 알려 줬나 | 알림 시작부터 6분 안에 회신한 장애 / 회신한 장애 | 위와 같음 | 가능 |
| 처리 성공 | 멈추지 않았나 | 끝까지 처리돼 회신한 장애 / 접수 후 15분 지난 장애 | `incidents.status`, `report_ts` | 가능 |
| 처리 결과 정확도 | 판단이 맞았나 | 처리 결과(자동 수정, 사람 확인, 런북 안내)가 맞은 장애 / 처리한 장애 | 실험 결과 CSV의 기대 결과 | 실험에서만 |
| 자동 수정 정확도 | 판단이 맞았나 | 자동 수정이 맞았던 장애 / 자동 수정으로 끝난 장애 | 위와 같음 | 실험에서만 |

### 정의에서 정한 것

- **회신 시간은 알림 시작부터 잰다.** 장애가 실제로 시작된 시각은 운영에서 알 수 없다. 장애 시작부터 알림까지(감지 구간)는 실험 실행기(`scripts/run_cluster.py`)가 장애를 넣은 시각으로만 잴 수 있다.
- **회신 시간은 장애 유형별로 나눈다.** 코드 버그는 코드를 고쳐야 하는 장애(자동화가 수정안을 만들고 테스트한다), 설정·인프라 장애는 코드 수정 없이 설정, 자원, 노드, 외부 연동 쪽에서 풀어야 하는 장애(자동화가 런북을 안내한다)다. 구분은 분류 단계의 `needs_code_fix`다. 3-7 실측에서 장애 발생부터 회신까지 중앙값은 코드 버그 120초, 설정·인프라 장애 264초였다. 합치면 어느 쪽이 느려졌는지 보이지 않는다.
- **3분과 6분은 임시 기준이다.** 3-7 실측 중앙값에 여유를 둔 값이다. 4단계에서 SLO를 정할 때 다시 정한다.
- **자동 수정 정확도는 처리 결과 정확도와 따로 본다.** 사람에게 넘길 장애를 잘못 넘기면 회신이 늦어질 뿐이지만, 고치면 안 되는 장애를 자동 수정하면 잘못된 수정이 배포될 수 있다. 목표치도 더 엄격해야 한다. 3-7의 S08(거짓 통과)이 이 경우다.
- **중복 회신은 처리 성공의 실패로 센다.** 운영 데이터에는 회신이 한 번만 남아서(`report_ts`) 중복을 셀 수 없다. 실험 실행기가 회신 채널의 Slack 메시지 수로 센다. 3-7 S16에서 한 장애가 두 번 회신된 것을 이렇게 찾았다.

### 측정 공백

- **커버리지.** Alertmanager는 해소된 알림을 오래 들고 있지 않고, Loki 규칙의 알림은 Prometheus `ALERTS`에도 남지 않는다. 그래서 "라우팅된 알림 수"를 나중에 셀 수 없다. 지금은 웹훅 전달 성공률로 근사한다. 4단계 전에 Alertmanager 웹훅을 받는 쪽에서 받은 알림을 모두 기록할지(접수하지 않은 것 포함) 정한다.
- **정확도 두 개.** 정답(기대 결과)이 시나리오 파일에만 있다. 운영에서는 회신 카드에 담당자가 "맞음 / 틀림"을 누르는 피드백이 있어야 계산할 수 있다. 4단계 전에 수집 방법을 정한다.

## 초기 목표(SLO 초안)

아래 값은 운영 데이터로 정한 SLO가 아니다. 운영 트래픽이 없어서, 3단계 실측(실험 수십 건)에서 출발해 정한 가설이다. 실제 운영을 시작하면 28일 동안 측정한 뒤 다시 정한다.

### 정하는 방법

1. **사용자 질문에서 출발한다.** 위 SLI 표의 네 질문이다.
2. **지금 대체로 지키는 수준에서 시작한다.** 지키지 못할 목표는 경보만 울리고 무시된다.
3. **사용자가 불편해지는 선을 본다.** 담당자가 직접 로그를 봐도 5~10분이면 원인을 잡는다. 자동 회신이 그보다 늦으면 쓸모가 없다.
4. **틀렸을 때의 피해에 따라 엄격함을 다르게 한다.** 잘못된 자동 수정은 배포 위험이 있어 가장 엄격하다.
5. **기간은 28일 롤링이다.** 에러 예산(1 - 목표)을 다 쓰면 기능 추가를 멈추고 안정화한다.

### 목표

| SLI | 목표(28일) | 근거 |
| --- | --- | --- |
| 웹훅 전달 | 99.9% | 3단계 실측 100%. 놓치면 장애를 아예 모른다 |
| 회신 시간(코드 버그, 3분) | 90% | 3단계 실측 83%. 놓친 2건은 노드 장애 중이다. 사람 대응(5분 이상)보다 빨라야 한다 |
| 회신 시간(설정·인프라 장애, 6분) | 90% | 같은 방식 |
| 처리 성공(15분 안 회신) | 99% | 멈춘 장애는 담당자가 모른다 |
| 처리 결과 정확도 | 90% | 3단계 실측 94% |
| 자동 수정 정확도 | 95%, 거짓 통과 0건 | 잘못된 수정은 배포될 수 있다. S08이 이 경우다 |

### 아직 하지 않은 것

- 에러 예산 소진 속도(burn rate) 알림은 만들지 않았다.
- 커버리지와 정확도 두 개는 운영 데이터로 셀 수 없다(위 측정 공백). 목표는 실험 결과로만 확인한다.

## SLI가 아닌 지표

- **장애당 LLM 비용**은 사용자가 체감하는 품질이 아니다. 운영 제약(가드레일)으로 따로 본다.
- **큐 대기 수, DLQ, 모델별 호출 비율**은 SLI가 나빠졌을 때 원인을 찾는 지표다. 대시보드의 접힌 행에 둔다.

## 계산

```
.venv/bin/python -m scripts.sli_report --since 2026-11-14 --results results/phase3.csv
```

운영 데이터(PostgreSQL, Prometheus)로 셀 수 있는 SLI는 클러스터에서, 정확도 두 개는 실험 결과 CSV에서 센다. Grafana 자동화 대시보드의 첫 줄이 같은 정의를 쓴다.

## 4단계로 넘기는 것

- SLI마다 목표치(SLO)와 기간. 초기 목표는 위에 정했다. 운영 데이터로 다시 정한다
- 에러 예산 소진 속도(burn rate) 알림
- 커버리지를 셀 알림 기록과 정확도를 셀 담당자 피드백
