# 3단계 알림 경로 첫 실제 사례(PodOOMKilled)

2026-11-14 KST 21시 25분. 사람이 넣은 알림이 아니라 클러스터에서 실제로 난 장애가 알림으로 감지돼 자동화까지 이어진 첫 사례다.

## 경위

1. 런북 검색을 확인하려고 api 컨테이너 안에서 임베딩 모델을 올리는 프로세스를 하나 더 실행했다. api 프로세스는 직전의 지식 문서 수집으로 이미 모델을 올린 상태였다. 그래서 컨테이너가 메모리 limit(768Mi)을 넘어 OOMKilled로 재시작됐다.
2. Prometheus의 `PodOOMKilled` 규칙(3-4에서 추가)이 firing이 됐다. Alertmanager는 지금 라우팅(aiops namespace 전체)에 따라 `ai-automation`으로 보냈다.
3. 자동화가 장애로 접수했다. `source=alertmanager`, `alertname=PodOOMKilled`이고, 대상 서비스는 `container` 라벨에서 꺼낸 `api`다.
4. 워커가 분류(Haiku 5.5) 1회 뒤 비코드 장애로 판단해 런북 안내로 끝냈다. 접수부터 완료까지 5초, $0.000286이었다.
5. #aiops-report에 카드가 올라갔다(`report_ts` 기록).

## 찾은 문제와 수정

- 분류는 `config`(신뢰도 0.40)였다. 그런데 Kubernetes 런북이 카테고리 `infra`에 묶여 있어서, OOM 런북 대신 기동 실패 런북(`k8s/crashloop.md`)이 안내됐다.
- Kubernetes 런북 4개의 카테고리를 `general`로 바꿨다. 이 런북들은 분류 결과가 아니라 알림 이름과 증상으로 찾아야 한다. `general`은 검색 필터가 항상 포함한다.
- 바꾼 뒤 클러스터 DB에서 검색을 다시 확인했다. 알림 5개 유형 모두 맞는 런북이 1위로 나왔다. 그중에는 OOM이 `config`로 분류된 경우도 있다.

## 코드 버그 알림 경로(S01, ShopapiException)

2026-11-14 KST 21시 39분. 알림 라우팅을 알림 이름으로 좁힌 뒤(infra_local_set PR #3) 코드 버그 경로를 확인했다. 사람이 한 일은 S01 버그 이미지(`s01-859b7f2-d600a24`)를 배포하고 요청 1건을 보낸 것뿐이다.

| 시각(UTC) | 단계 |
| --- | --- |
| 12:39:54 | `POST /orders/summary`(빈 주문) 요청이 500으로 끝나고 ERROR 로그가 남음 |
| 12:41:06 | Loki 규칙 `ShopapiException`이 firing이 되고 자동화가 장애 `17a9872dbd6a`로 접수. 스택트레이스(`ZeroDivisionError`)는 Loki에서 붙임 |
| 12:41:33 | 분류($0.0002), 원인 분석($0.0543), 수정 생성($0.0265) 뒤 테스트 7개 통과. 1회 시도로 resolved, 합계 약 $0.081 |
| 12:41:36 | Alertmanager가 알림 해소를 보내 `alert_resolved_at` 기록 |

#aiops-report에 카드가 올라갔다(`report_ts` 기록). 확인 뒤 클러스터는 버그 없는 이미지(`base-859b7f2`)로 되돌렸다.

**패치 판정.** 자동화가 만든 패치를 숨은 테스트로 로컬에서 다시 판정했다. 숨은 테스트 3개, 전체 43개가 모두 통과했다. 거짓 통과가 아니다. 패치는 `average_unit_price`에서 수량이 0 이하면 0.0을 돌려주는 2줄 추가다.

**판정할 때 주의할 점.** `judge`는 버그가 이미 주입된 shopapi에 패치를 적용한다. 실험 스크립트는 `injected()` 안에서 부르지만, 따로 부를 때 이를 빼면 컨텍스트가 맞지 않아 "패치 적용 실패"가 나온다. 처음 판정에서 이 실수로 실패가 나왔다. DB에서 패치를 꺼낼 때도 `psql -tA`는 끝에 빈 줄을 하나 더 붙이므로, base64로 꺼내야 원문과 같다.

**알림 해소 시각의 의미.** `alert_resolved_at`은 Alertmanager의 `endsAt`이다. `ShopapiException`은 1분 창의 ERROR 수를 세는 규칙이라, 요청 1건의 에러는 창을 벗어나면 저절로 해소된다. 이번 해소는 수정 배포 때문이 아니다. 해소 시각으로 수정 효과를 판단하려면 에러가 계속 나는 상태에서 확인해야 한다.
