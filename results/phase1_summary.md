## 비용 차이의 출처

행 기준으로 A가 B보다 $0.32(28%) 싸다. 출처를 시나리오 유형별로 나누면 합이 전체 차이와 맞는다(측정). 각 출처를 어떤 최적화가 만들었는지는 두 조건의 설정 차이와 모델별 호출 수로 추정한 것이다.

| 출처 | 차이 | 원인 |
| --- | --- | --- |
| 코드 버그 9건 | $0.13 | 건당 $0.095 → $0.081. 입력 토큰은 두 조건 모두 평균 약 10,300개로 같다. 분류를 Opus 대신 Haiku로 한 차이로 추정(모델 분리) |
| 비코드 장애 2건(S10, S11) | $0.09 | 건당 $0.044 → $0.0003. B는 Opus로 분류하고 원인 분석까지 부른다(호출 수로 확인, 조기 종료와 모델 분리로 추정) |
| 재발(S12) | $0.09 | A는 검증된 수정안을 재사용해 LLM 0회(수정안 재사용) |
| 중복(S13) | $0.02 | 처리된 1건의 분류 모델 차이 |

개별 최적화의 기여는 이 시나리오 구성에서의 값이다. 비코드 장애와 재발이 많은 운영 환경이면 차이가 더 커지고, 코드 버그뿐이면 분류 모델 차이(건당 약 $0.014)만 남는다(추정).

## 정확도와 거짓 통과

- 코드 버그 9건 모두 첫 시도에 수정안을 냈다. plan.md 4장이 에스컬레이션을 예상한 S08(시그니처 불일치), S09(순서 의존)도 A에서는 숨은 테스트까지 통과했다.
- B의 S08은 거짓 통과다. 패치가 `reserve`에 `order_id` 인자만 추가하고 예약 기록에는 저장하지 않았다. 전체 공개 테스트는 통과했지만 주문 ID 기록을 확인하는 숨은 테스트에서 실패했다. A의 S08 패치는 `Reservation`에 필드를 추가하고 기록까지 했다. 두 조건 모두 수정 생성은 같은 Opus 5.5가 했으므로, 이 차이를 최적화 때문이라고 볼 근거는 없다. 1회 실행의 LLM 결과 흔들림으로 본다(추정). 숨은 테스트가 없었다면 이 수정은 성공으로 집계됐다.
- 분류 정확도 12/13의 한 건은 두 조건 모두 S10이다. 외부 PG 지연을 `dependency`로 분류했다(기대값 `infra`). 결과는 둘 다 런북 안내(no_code_fix)로 맞다. 기대값은 고치지 않았다(decisions/0011).

## 기록 결함과 원인 미확인

- 재발(S12) 행에는 재접수 건 비용만 남고 base(S01) 처리 비용이 빠졌다. 상태 저장소에서 찾은 base 비용은 A $0.0813(incident 6a766eb6c7c5), B $0.0855(incident 07b6517146c1)다. 위 "실제 쓴 비용"은 이를 더한 값이다. 실험 스크립트는 이후 `procedure_usd` 열로 절차 전체 비용을 남기고 비용 상한도 이 값으로 센다(PR #7).
- B의 S12는 약 18분 걸렸다. base 처리는 20:42:13(UTC)에 끝났고, 재접수 건의 처리 시간이 30.2초이므로 재접수는 약 20:58:45에 일어났다. 그 사이(base 판정, 원복, 재주입, 재현)에서 16분이 지났다. 실험 뒤 컨테이너를 다시 만들어 워커 로그가 남지 않아 원인은 확인하지 못했다. 이후 실행은 끝날 때마다 워커 로그를 결과 폴더에 저장한다.

## 시간

- 처리 시간은 LLM 응답 시간이 대부분이다. 비코드 장애는 A에서 3~6초, B에서 15~21초였다(B는 Opus 분류와 원인 분석).
- 테스트 선별의 시간 효과는 이 대상에서 작다. shopapi 테스트는 7개 파일, 전체 실행이 0.8초 안팎이라 선별해도 0.1초 정도 차이다. 선별의 효과를 보려면 테스트가 더 큰 대상이 필요하다.

## 한계

- 시나리오와 숨은 테스트를 같은 사람이 만들었다(decisions/0004).
