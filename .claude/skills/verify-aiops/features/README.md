# AI 장애 대응 자동화 검증 지도

검증할 때 먼저 이 색인을 읽고, 맞는 기능 파일을 절차로 쓴다. 이 지도가 검증의 기준이다. 편한 진입점 하나만 확인한 증명은, 지도에 다른 진입점이 있으면 완료가 아니다.

## 기본 전제

- `launch.sh`로 띄운 aiops-verify 스택(api 18000, shopapi 18100)이고 `doctor.sh`가 모두 OK다.
- 이 검증이 띄우지 않은 인스턴스는 조작하지 않는다. 사용 중인 스택(8000, 8100)은 실험용이다.
- 기본은 가짜 LLM이다. 실제 LLM이 필요한 기능은 파일에 적혀 있다.

## 실행 규칙

- 모든 명령은 저장소 루트에서 그대로 실행한다.
- 시나리오 실행은 `drive.sh`, 단건 확인은 curl로 한다.
- 각 시나리오는 실행 전에 캐시를 비우므로 순서와 무관하다. 재발(S12)만 base(S01)를 자체 절차 안에서 먼저 돈다.

## 증명과 건너뜀 보고

- 증거는 `results/verify/<RUN_ID>/`의 runs.csv 행과 incident JSON이다.
- 실행하지 못한 진입점은 시도한 명령과 충족되지 않은 전제를 적는다. 다른 경로로 확인했다고 보고하지 않는다.

## 기능 항목 형식

각 파일은 H1 제목과 사용자에게 보이는 동작 한 단락, 그리고 `Sub-features`, `How to get to it (user POV)`, `Driving it with verify-aiops`, `Gotchas` 네 개의 H2로 이뤄진다.

## 기능

- [장애 접수와 중복 제거](incident-intake.md)는 API 접수, 토큰 인증, 같은 알림 묶기, 상태 조회를 다룬다.
- [비코드 장애 런북 안내](runbook-exit.md)는 알림 문구와 기동 실패 장애가 고성능 모델 없이 런북 안내로 끝나는지 다룬다.
- [코드 버그 자동 수정](code-fix-loop.md)은 분류, 원인 분석, 수정, 선별 테스트, 숨은 테스트 판정을 다룬다(실제 LLM 필요).
- [재발 시 수정안 재사용](fix-reuse.md)은 같은 장애가 다시 올 때 LLM 없이 처리되는지 다룬다(실제 LLM 필요).
- [실험 조건 확인](experiment-config.md)은 최적화 설정 조회와 조건 불일치 시 실험 중단을 다룬다.
